# Issue 品質ゲート

Issue は「何を変えるか」だけを並べる作業メモではありません。第三者が、なぜ今その作業が必要で、何を根拠に判断し、どの状態になれば完了かを検証できる追跡単位です。

## 1. 適用範囲

この文書は、WordPackのIssue本文に記載する理由、根拠、ユーザー体験、範囲、受け入れ条件の品質基準です。Issueを作成・更新・参照する判断やタイミングは利用環境のローカル規則とユーザー依頼に従います。

## 2. 必須内容

該当する `.github/ISSUE_TEMPLATE/` を使い、少なくとも次を記載します。

1. 背景と判断理由
   - なぜ必要か。
   - なぜ今対応するか。
   - 対応しない場合に誰がどこで困るか。
2. 根拠と不確実性
   - 確認済み事実。
   - ユーザーから提示された判断材料。
   - コード、公式仕様、ログ、実データなどの出典。
   - 仮説、推定、未確認事項。
3. 現状の問題と影響
   - 現在の挙動または制約。
   - 利用者、運用、保守、データ、セキュリティへの影響。
4. 現在と対応後のユーザー体験
   - 対象ユーザー、利用文脈、達成したいこと。
   - 現在ユーザーが経験していることと、その結果生じている認識、負担、感情、体験状態。
   - 対応後に何が変化し、何を理解、判断、実行、回復できるようになり、最終的にどのような体験状態になるか。
   - ユーザー申告、実ユーザー観察、観測事実からの推定、未確認の仮説のどれに基づく記述か。
5. 目的と期待する成果
   - 実装項目ではなく、作業後に成立させたい状態。
6. 対応範囲と非対象
   - 今回行うこと。
   - 意図的に行わないことと、その理由。
7. 受け入れ条件と検証方針
   - 第三者が Pass / Fail を判定できる条件。
   - 各条件を確認するテスト、画面、ログ、文書、手動確認。
8. リスクと未確認範囲
   - 既存挙動への影響。
   - 実行できない検証。
   - 完了後にも残る不確実性。

## 3. 事実・判断材料・仮説の分離

Issue では、次を同じ事実として混ぜません。

| 種別 | 書き方 |
|---|---|
| 確認済み事実 | 何を、どの証跡で確認したかを書く |
| ユーザー提示の判断材料 | 依頼時に提示された情報であり、リポジトリ側で再検証したかを明記する |
| 判断 | どの事実・目的・制約から、その方針を選んだかを書く |
| 仮説・推定 | 未確認であることと、確認方法を書く |
| 未確認事項 | 確認できない理由、影響、次の最短アクションを書く |

外部評価や第三者資料を使う場合、出典を示すだけで確認済み事実に格上げしません。現行仕様や高リスクな判断は、可能な限り公式資料、コード、テスト、ログ、実データで確認します。

## 4. ユーザー体験の記載方法

「現在のユーザー体験」と「対応後に目指すユーザー体験」は、同じ対象ユーザーと利用文脈を基準に対で記載します。機能名、変更ファイル、実装方法の説明だけで代替してはいけません。

### 現在のユーザー体験

- 対象ユーザーと、そのユーザーが置かれている利用文脈を特定する。
- ユーザーが達成したいことと、現在実際に見聞きし、判断し、操作し、待機し、失敗し、回復していることを書く。
- その過程で生じる認識、迷い、負担、不安、安心、信頼と、最終的に置かれる体験状態を書く。
- 感情や主観を直接確認していない場合は断定せず、ユーザー申告、実ユーザー観察、観測事実からの推定、未確認の仮説のどれかを明示する。

### 対応後に目指すユーザー体験

- 同じ対象ユーザーと利用文脈で、何がどのように変わるかを書く。
- ユーザーが新たに、またはより確実に理解、判断、実行、回復できることを書く。
- 手数や待ち時間だけでなく、結果として得られる認識、負担、安心、信頼などの体験状態を書く。
- 目指す変化を受け入れ条件へ接続し、画面、操作、テスト、計測、手動確認などで確認する方法を書く。

### 体験が直接変わらない Issue

調査、内部改善、保守、ガバナンスなどで製品利用者の体験が直接変わらない場合も、記載自体を省略しません。「直接的なユーザー体験の変化はない」と理由を明記し、後続の判断や変更を通じて目指す体験がある場合は分離して書きます。

開発者や運用者の作業効率だけを、製品利用者の体験向上として言い換えてはいけません。直接の対象が開発者や運用者である場合は、その対象を明示します。

## 5. 判断の記録品質

Issue本文を判断根拠として使う場合、記載内容は理由、既知の事実、判断、範囲、受け入れ条件、未確認事項を読み分けられるようにします。PRなど別文書の情報を根拠とする場合は、参照先とIssue本文で確認できない内容を区別します。

## 6. 公開安全性

Issue は公開され得る文書として扱います。根拠を示すために、秘密情報、認証情報、個人情報、ユーザー入力全文、本番ログ原文、追跡可能な識別子を貼ってはいけません。

公開できない根拠は、次の粒度で要約します。

- 確認した証跡の種別。
- 公開可能な観測事実。
- 判断への影響。
- 公開できない範囲。
- 必要な次の確認。

詳細は `docs/security-publication-checklist.md` を正本とします。

## 7. Issue / PR の日本語品質

Issue と PR のタイトル・本文は日本語を原則とします。固有名詞、製品名・ライブラリ名、`code identifier`、`version/path`、GitHub構文に加え、`[Bug]`、`[Feature]`、`[Investigation]`、`[Ops]` など一般的なIssueカテゴリの接頭辞は原表記を維持できます。接頭辞に続く要約と判断に必要な説明は日本語で書き、英語表記は識別子、構文、一般的なカテゴリに限定します。

タイトルは、対象と変更または問題が判別できる具体性を持たせます。`改善`、`対応`、`update` のように対象や結果が分からない短い語だけをタイトルにしません。本文には、このIssueまたはPRで第三者が確認すべき理由、根拠、現在と目標、範囲、非対象、受け入れ条件、検証、リスクを日本語で記録します。

Dependabotなどの自動生成bot PRでは、初期タイトル・本文が日本語でない場合があります。人が記載・編集するIssue / PRの内容はこの原則に従います。native設定が保証するのは設定可能なprefixやlabelまでで、本文の完全な日本語化を設定だけで保証しません。

## 8. レビュー指摘をIssue本文に記録する場合

Issue本文にreview findingを記録する場合は、参照先に加えて、severity、観測事実、影響、現在と目標のユーザー体験、scope、受け入れ条件、検証方法を示します。参照URLだけでは、観測事実やfindingの由来を示したことになりません。

P0 / P1、security、secret、data integrity、または必要な受け入れ証跡の矛盾がある場合は、その影響と解消条件をIssue本文で明確にします。追跡するIssueの選択、作業scope、blocking状態の扱いは、ユーザー依頼と利用環境のローカル規則に従います。

## 9. Pass / Fail

### Pass

- 第三者が、理由、根拠、期待成果、範囲、非対象、受け入れ条件、検証、リスクを読み取れる。
- 確認済み事実と未確認事項が分離されている。
- 同じ対象ユーザーと利用文脈について、現在と対応後の体験状態を比較できる。
- ユーザーの認識、負担、感情に関する記述の根拠区分が明示されている。
- 受け入れ条件が実装項目の言い換えではなく、観測可能な結果になっている。
- 公開してはいけない情報を含まない。

### Fail

- 変更ファイルや実装項目だけが並び、なぜ必要か分からない。
- 「改善する」「対応する」だけで、誰の何がどう良くなるか分からない。
- 「使いやすくなる」「安心できる」だけで、現在と対応後の体験の差が説明されていない。
- 未確認のユーザーの感情や主観を、確認済み事実として断定している。
- 現在と対応後で対象ユーザーや利用文脈がすり替わっている。
- 外部情報、ユーザー提示情報、仮説を確認済み事実として断定している。
- 非対象がなく、作業範囲が際限なく広がる。
- 受け入れ条件がなく、完了を客観的に判定できない。
- 検証できない範囲や残るリスクを隠している。

Failに該当する項目はIssue本文の不足として示します。作業の開始・追跡方法はユーザー依頼と利用環境のローカル規則に従います。
